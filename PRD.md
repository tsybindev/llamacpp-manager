# PRD: LlamaCpp Manager (рабочее название)

## 1. Обзор проекта

Кроссплатформенное десктоп-приложение (Windows, Linux: Ubuntu/Arch) с графическим интерфейсом для управления локальным `llama.cpp` сервером (`llama-server`):

- скачивание и обновление сборок `llama.cpp` под разные бэкенды (Vulkan, CUDA, ROCm/HIP, CPU-only и т.д.);
- поиск и скачивание моделей (GGUF) с HuggingFace;
- запуск/остановка сервера с гибкой настройкой параметров;
- сохранение конфигураций (пресетов) для быстрого переключения между моделями/режимами;
- оценка потребления RAM/VRAM до запуска, чтобы не ловить OOM.

Целевая аудитория — технически подкованные пользователи (энтузиасты локальных LLM), которым не нужен визард "для чайников", но нужен удобный инструмент вместо ручного набора CLI-флагов и bat/sh-скриптов.

**Контекст использования:** приложение работает как локальный менеджер одного `llama-server`, поверх которого стоит внешний стек (litellm как прокси/роутер, langfuse для трейсинга). Из этого следует:
- сервер должен быть стабильным, с предсказуемым адресом/портом — litellm ходит к нему как к обычному OpenAI-совместимому эндпоинту;
- важны логи и индикация состояния (health-check), т.к. падение сервера должно быть сразу заметно;
- встроенный чат/UI поверх API не нужен — это делает внешний стек;
- телеметрия самого приложения не нужна.

## 2. Технологический стек

**Rust + egui (через `eframe`)**

Обоснование:
- immediate-mode GUI хорошо подходит для формы с десятками параметров (чекбоксы, слайдеры, тултипы с описанием) — это основной сценарий использования приложения;
- минимальный footprint по RAM (нет рантайма/GC/браузерного движка), быстрый холодный старт;
- один кодбейс под Windows/Linux (winit: X11 + Wayland);
- простая модель для агентной генерации кода (нет сложной message-passing архитектуры, как в Iced/Elm);
- удобно оборачивать вызовы внешних процессов (`std::process::Command`) и системные вызовы (проверка GPU, свободного места на диске, ОЗУ).

Вспомогательные крейты (ориентировочно):
- `tokio` + `reqwest` — асинхронные загрузки (модели, бинарники llama.cpp), с поддержкой resume (Range-запросы) и прогресс-бара;
- `serde`/`serde_json` — конфиги, пресеты, кэш метаданных HF;
- `sysinfo` — определение объёма RAM, загруженности;
- обнаружение GPU и VRAM: `nvml-wrapper` (NVIDIA), парсинг `vulkaninfo`/`wgpu` adapter info (для Vulkan/AMD/Intel), на Linux — fallback на `lspci`/`/sys`;
- `directories` — кроссплатформенные пути (конфиги, кэш, модели). Отдельный keyring-крейт не нужен — токен HF хранится в обычном конфиг-файле;
- `self_update` или ручная логика — обновление самого приложения (опционально, вне MVP).

Альтернативы, отклонённые на этом этапе: Tauri (лишний веб-слой ради не самого сложного UI), Iced/Slint (меньше поддержки для агентной генерации, более многословный код состояния).

## 3. Цели

- Убрать ручной ввод CLI-команд для запуска `llama-server`.
- Дать безопасный способ подбирать параметры (с описанием и возможностью отключить/сбросить к дефолту).
- Автоматизировать получение сборок `llama.cpp` под конкретное железо пользователя.
- Автоматизировать поиск/скачивание GGUF-моделей с HuggingFace без похода в браузер.
- Предупреждать о нехватке VRAM/RAM до запуска модели.

## 4. Не цели (Out of scope, MVP)

- Не является inference-движком — вся генерация делегируется `llama-server`.
- Не поддерживает finetuning/quantization моделей (только скачивание готовых GGUF).
- Нет мультипользовательского/серверного режима (одно приложение = один локальный пользователь).
- Нет встроенного чат-интерфейса поверх сервера (можно рассмотреть отдельно, как plus-фичу после MVP — просто кнопка "открыть в браузере" на веб-UI llama-server или на связанный сторонний фронтенд).

## 5. Функциональные требования

### 5.1 Управление сборками llama.cpp

- Автоопределение платформы (OS, CPU-архитектура) и доступного GPU-бэкенда:
  - NVIDIA → CUDA-сборка (плюс fallback Vulkan);
  - AMD → ROCm/HIP (Linux) или Vulkan (Windows/Linux);
  - Intel iGPU/Arc → Vulkan/SYCL;
  - нет дискретной GPU → CPU-сборка (с учётом AVX2/AVX512 при наличии).
- **Приоритет для MVP: Vulkan.** Целевое железо разработки/эксплуатации — AMD RX 6800XT (Linux, Vulkan) и NVIDIA RTX 3090 (Windows). Vulkan-сборка работает на обеих картах без лишних телодвижений (ROCm ставится не всегда гладко на Arch/Ubuntu, CUDA требует отдельного набора драйверов/toolkit) — значит один и тот же путь кода закрывает обе машины сразу. CUDA-сборку для RTX 3090 можно добавить позже вторым вариантом (обычно даёт прирост производительности над Vulkan на NVIDIA), но это не блокер MVP.
- Список доступных релизов подтягивается с GitHub Releases репозитория `ggml-org/llama.cpp` (или зеркала) — парсинг ассетов по имени (win-vulkan-x64, win-cuda-cu12.4-x64, ubuntu-vulkan-x64, и т.д.).
- Ручной выбор варианта сборки (на случай, если автоопределение ошиблось или пользователь хочет протестировать другой бэкенд).
- Кэш скачанных версий, возможность держать несколько версий одновременно и переключаться.
- Проверка контрольных сумм/подписи релиза, если доступны.
- Уведомление о новых версиях (без автообновления по умолчанию — явное подтверждение пользователя).

### 5.2 Управление моделями (HuggingFace)

- Поиск моделей по названию/тегам через HF API (`/api/models`, фильтр по `library=gguf` или наличию `.gguf` файлов в репозитории).
- Просмотр списка файлов конкретного репозитория с фильтром по квантованию (Q4_K_M, Q5_K_S, Q8_0 и т.д.), отображение размера файла.
- Скачивание выбранного файла с прогресс-баром, поддержкой докачки (resume) и ограничением скорости (опционально).
- Поддержка приватных/gated-моделей через HF token (хранится локально, желательно через системный keyring, не в открытом конфиге).
- Локальная библиотека скачанных моделей: путь, размер, дата, источник (repo/файл), возможность удалить/переместить.
- Определение метаданных модели из GGUF-заголовка (архитектура, число слоёв, n_embd, context length по умолчанию, квантование) для последующего расчёта памяти — без необходимости скачивать весь файл (частичное чтение заголовка через Range-запрос при наличии, либо после закачки).

### 5.3 Управление сервером

- Старт/стоп/рестарт `llama-server` как дочернего процесса.
- Вывод логов процесса в реальном времени (stdout/stderr) в отдельной панели, с возможностью сохранить лог в файл.
- Индикация состояния: запускается / готов (health-check по `/health` или порту) / упал с ошибкой.
- Настройка порта, host (127.0.0.1 по умолчанию, опция 0.0.0.0 с явным предупреждением о рисках).
- Быстрый доступ: кнопка "открыть в браузере" (веб-UI llama-server) и копирование адреса API.

### 5.4 Конфигурация параметров

- Каталог параметров `llama-server` (например: `--ctx-size`, `--n-gpu-layers`, `--batch-size`, `--threads`, `--flash-attn`, `--mlock`, `--no-mmap`, `--rope-freq-base`, `--cache-type-k/v`, и т.д.), для каждого:
  - человекочитаемое название и описание (тултип/подсказка), включая единицы измерения и допустимый диапазон;
  - тип виджета: чекбокс (bool-флаги), слайдер/числовое поле (int/float), выпадающий список (enum, например тип кэша);
  - переключатель "включено/выключено" — отключённый параметр не передаётся в командную строку (используется дефолт самого llama.cpp), а не передаётся с "дефолтным" значением. Это важно, т.к. дефолты могут меняться между версиями llama.cpp;
  - значение по умолчанию, которое подставляется при включении.
- Каталог параметров обновляемый (JSON/TOML-файл, поставляется с приложением, с возможностью community-обновления/переопределения пользователем без пересборки приложения).
- Предпросмотр итоговой команды запуска (сгенерированная командная строка) перед стартом — для прозрачности и отладки.
- Валидация значений (диапазоны, зависимости между параметрами, например `--n-gpu-layers` бессмысленен без GPU-сборки).

### 5.5 Пресеты

- Сохранение именованного пресета: выбранная модель + путь к сборке llama.cpp + набор включённых параметров и их значений.
- Быстрая загрузка пресета одним кликом (заполняет форму, не запускает автоматически — запуск отдельным действием, либо опция "загрузить и сразу запустить").
- Импорт/экспорт пресетов (JSON-файл) для переноса между машинами/шаринга с другими пользователями.
- Дублирование/переименование/удаление пресетов.

### 5.6 Расчёт использования памяти

Оценка (до запуска) на основе:
- размера файла модели (веса) — как приближение к RAM/VRAM под веса, с поправкой на mmap/no-mmap;
- KV-кэша: `n_layers * n_ctx * n_kv_head * head_dim * 2(K+V) * bytes_per_element`, с учётом `--cache-type-k/v` (f16/q8_0/q4_0 и т.д.) и GQA (n_kv_head может быть меньше n_head);
- распределения слоёв между GPU/CPU при частичной выгрузке (`--n-gpu-layers`) — отдельный расчёт VRAM (выгруженные слои + их доля KV-кэша) и RAM (оставшиеся слои);
- служебных накладных расходов (compute buffers, batch buffers) — приближённая эвристика/константа с оговоркой "оценка приблизительная".
- Отображение результата: "Модель + контекст X токенов ≈ Y ГБ VRAM / Z ГБ RAM", с цветовой индикацией (зелёный — укладывается в доступную память, жёлтый — впритык, красный — не хватает по данным `sysinfo`/`nvml`).
- Это именно оценка, UI явно помечает её как приблизительную (реальное потребление зависит от версии llama.cpp, батч-параметров и т.д.).

### 5.7 Общие настройки приложения

- Пути: директория для моделей, директория для бинарников llama.cpp, директория логов.
- HF-токен (простое хранение в локальном конфиг-файле, без системного keyring — проще в реализации; файл кладётся в директорию конфигов пользователя с ограниченными правами доступа, приложение явно предупреждает, что токен хранится в открытом виде).
- Автовосстановление сервера: тумблер вкл/выкл, макс. попыток рестарта (по умолчанию 3), окно времени (по умолчанию 5 минут), задержка между попытками (по умолчанию экспоненциальный backoff от ~2 сек).
- Источник каталога параметров: URL raw JSON (с дефолтным значением из коробки, редактируемым для зеркала/своего хостинга).
- Тема интерфейса (светлая/тёмная), масштаб UI (для HiDPI).
- Язык интерфейса (минимум EN, желательно RU).

## 6. Нефункциональные требования

- Потребление RAM самим приложением (без модели/сервера) — целевой ориентир: до ~100–150 МБ в простое.
- Холодный старт приложения — до ~1 секунды на средней машине.
- Работа без интернета для уже скачанных моделей/бинарников (сетевые запросы только для поиска/скачивания нового).
- Устойчивость к обрыву сети при скачивании — докачка, а не рестарт с нуля.
- Корректное завершение дочернего процесса `llama-server` при закрытии приложения (SIGTERM/graceful shutdown, таймаут → kill).
- Поддержка Wayland и X11 на Linux.
- Открытый формат конфигов/пресетов (человекочитаемый JSON/TOML) — не проприетарный бинарный формат.

## 7. Высокоуровневая архитектура

```
app/
├── ui/            # egui-виджеты: экраны (модели, сборки, параметры, пресеты, логи, настройки)
├── core/
│   ├── hf_client/     # HF API: поиск, метаданные, скачивание
│   ├── release_fetcher/  # GitHub Releases llama.cpp: список, скачивание, определение платформы
│   ├── process_mgr/   # запуск/остановка llama-server, чтение stdout/stderr, health-check, автовосстановление при падении (лимит попыток, backoff)
│   ├── params/        # каталог параметров (загрузка из локального кэша + фоновая проверка обновлений из внешнего источника, слияние с user overrides), валидация, сериализация в CLI-аргументы
│   ├── presets/       # CRUD пресетов, импорт/экспорт
│   ├── mem_estimator/ # расчёт RAM/VRAM
│   └── gguf_meta/     # чтение заголовка GGUF (архитектура, n_layers, n_embd и т.д.)
├── config/        # пути, глобальные настройки, конфиг-файл (включая HF-токен в открытом виде)
└── main.rs
```

## 8. MVP vs следующие фазы

**MVP:**
- скачивание бинарников llama.cpp (ручной выбор варианта, без сложного автоопределения GPU);
- поиск/скачивание моделей с HF;
- запуск/остановка сервера, просмотр логов, автоматический рестарт при падении процесса (с лимитом попыток и backoff);
- базовый каталог из 10–15 самых используемых параметров с описаниями, загружаемый из внешнего источника с фоновой проверкой обновлений (и локальным кэшем на случай отсутствия сети);
- пресеты (сохранение/загрузка);
- простой расчёт памяти (веса + KV-кэш, без учёта частичной выгрузки).

**Фаза 2:**
- автоопределение GPU и рекомендация подходящей сборки;
- полный каталог параметров llama-server;
- расчёт памяти с учётом частичной выгрузки слоёв (`--n-gpu-layers`);
- импорт/экспорт пресетов, community-каталог параметров.

**Фаза 3 (опционально, низкий приоритет):**
- автообновление самого приложения;
- CUDA-сборка как дополнительный (не единственный) вариант для NVIDIA-машины, если Vulkan окажется узким местом по производительности.

Мультиинстансность (несколько `llama-server` одновременно) сознательно не планируется — сценарий использования всегда подразумевает ровно один активный сервер, поверх которого работает litellm.

## 9. Зафиксированные решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Поддержка macOS | Не требуется. Целевые платформы — только Windows и Linux (Ubuntu/Arch). |
| 2 | Встроенный чат-UI | Не нужен. Приложение — чистый менеджер сервера; логи и статус работы обязательны. |
| 3 | Приоритет GPU-бэкенда в MVP | Vulkan (закрывает и AMD RX 6800XT на Linux, и NVIDIA RTX 3090 на Windows одним путём кода). CUDA — опциональное улучшение производительности позже. |
| 4 | Несколько инстансов сервера | Не нужно ни сейчас, ни в перспективе — всегда ровно один активный `llama-server`. |
| 5 | Хранение HF-токена | Простое хранение в конфиг-файле (без системного keyring), с предупреждением, что это открытый текст. |
| 6 | Телеметрия | Не нужна. |
| 7 | Автовосстановление сервера | Нужен автоматический рестарт `llama-server` при падении процесса (важно, т.к. поверх работает litellm и падение не должно требовать ручного вмешательства). |
| 8 | Headless/автозапуск | Не нужен. Приложение всегда открывается вручную, GUI обязателен при каждом запуске. |
| 9 | Обновление каталога параметров | Обновляется отдельно от релизов самого приложения (не зашито намертво в бинарник) — чтобы новые флаги llama.cpp появлялись без ожидания новой версии менеджера. |
| 10 | Формат источника каталога параметров | Простой raw JSON-файл на статическом хостинге (без отдельного git-репозитория с PR-процессом). |
| 11 | Лимиты автовосстановления | Не хардкодятся — выносятся в настройки приложения (кол-во попыток, окно времени, задержка между попытками) с разумными значениями по умолчанию. |

### Уточнения к решениям 7, 9–11

**Настройки автовосстановления (п.11), добавить в раздел 5.7:**
- поля в настройках: "Макс. попыток рестарта" (по умолчанию 3), "Окно времени" (по умолчанию 5 минут), "Задержка между попытками" (по умолчанию: экспоненциальный backoff, стартуя с ~2 сек), "Включить автовосстановление" (общий тумблер вкл/выкл);
- при исчерпании лимита — сервер остаётся в состоянии "упал", автоперезапуск прекращается, в UI/логе явное уведомление, что лимит исчерпан и нужно вмешательство пользователя.

**Источник каталога параметров (п.10):**
- URL raw JSON задаётся в настройках приложения (с дефолтным значением "из коробки"), чтобы при необходимости можно было указать зеркало/свой хостинг;
- версия каталога — простое поле `version`/`updated_at` внутри самого JSON, по которому приложение решает, есть ли обновление относительно локального кэша.
